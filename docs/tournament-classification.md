# Класифікація турнірів: type і category

Статус: перехід на `type/category` опубліковано й застосовано до робочої БД 16.10.2026. Окреме очищення старих колонок реалізовано локально; на сервері ще не запускалося (розділ 12). Поточна видимість CCL уточнюється (розділ 11).

Документ фіксує цільову модель для `Admin → Tournaments` і `My Tournaments`.
На етапі 1 код, схема БД, API та дані не змінюються.

## 1. Поля класифікації

У цільовій моделі турнір має два поля класифікації:

- `type`: `Teams` або `Individuals`;
- `category`: одне зі значень, дозволених для вибраного `type`.

Наведені нижче значення є канонічними значеннями API та даних, а не лише
підписами у формі. Підписи для показу можна перекладати окремо.
Кожна категорія належить лише одному типу. Для нового запису обидва поля
обов'язкові; сервер перевіряє відповідність пари.

| type | category | Поведінка |
| --- | --- | --- |
| Teams | WTCOC | Зберегти чинну логіку офіційних турнірів збірних |
| Teams | ETCOC | Зберегти чинну логіку офіційних турнірів збірних |
| Teams | Asian Cup | Зберегти чинну логіку офіційних турнірів збірних |
| Teams | Copa America | Зберегти чинну логіку офіційних турнірів збірних |
| Teams | Friendly | Зберегти чинне самостійне планування матчів капітанами |
| Teams | Clubs | Спеціальну логіку реалізувати пізніше |
| Individuals | CCL | Спеціальну логіку реалізувати пізніше |
| Individuals | MSO | Спеціальну логіку реалізувати пізніше |
| Individuals | Rivals | Зберегти чинну логіку Rivals і зв'язки з Challenges |
| Individuals | National | Індивідуальні національні турніри; спеціальну логіку з вибором країни реалізувати пізніше |
| Individuals | King of Carcassonne | Спеціальну логіку реалізувати пізніше |

У формі спочатку вибирається `type`, після чого пропонуються його категорії.
Доступність спеціальних інструментів для майбутніх категорій реалізується
на наступних етапах; цей перелік сам по собі не активує нову турнірну логіку.

## 2. Відповідність старої моделі

| Старе поле або значення | Цільова модель |
| --- | --- |
| `tournament_type = Teams` | `type = Teams`; категорія визначається за чинним турніром |
| `tournament_type = Individuals` | `type = Individuals`; чинна категорія зберігається, крім перейменування `KoC` |
| `tournament_type = National` | `type = Individuals`, `category = National` |
| `tournament_type = Clubs` або командний турнір із `team_type = Club` | Цільова пара `Teams / Clubs`; наявність таких записів і збереження їхньої поведінки перевіряються перед міграцією |
| `category = KoC` | `category = King of Carcassonne` |
| `team_type` турніру | Прибрати як незалежне налаштування після переведення споживачів; вид команд визначається категорією |
| `subtype` і його legacy-дубль `access_type` | Прибрати як незалежні налаштування після переведення споживачів; правила доступу визначаються категорією та чинними ролями |

`tournament_type = National` означає індивідуальний національний турнір.
Його не можна плутати з `team_type = National`, яке зараз означає збірні
в командному турнірі.

`Local` не входить до нового переліку турнірних категорій. Це виправлення
попередньої пропозиції, а не вимога перейменувати спільну категорію `Local`
у новинах або іконках.

Типи самих команд у довіднику `teams` залишаються чинними: `National` і `Club`.
Видалення налаштування `team_type` у турніру не видаляє класифікацію команд.

## 3. Спільний довідник категорій

Залишається чинний спільний довідник `categories` для турнірів, новин та
іконок. Окремий незалежний довідник турнірних категорій не створюється.
Відповідність категорії типу та її поведінка є системними правилами,
а не додатковим налаштуванням окремого турніру.

Усі 11 категорій із розділу 1 мають бути позначені як турнірні та захищені
від редагування і видалення, включно з діями глобального адміністратора.
Read-only стосується всього запису категорії, зокрема `name`, `sort_order`
і `is_tournament`. Захист має працювати і в UI, і в API.
Створення та міграційні зміни цих системних записів виконуються кодом міграції.

Інші категорії спільного довідника зберігають чинну поведінку. Їхня наявність
або прапорець `is_tournament` самі по собі не додають нових дозволених пар
`type / category` до моделі з розділу 1.

Під час перейменування `KoC → King of Carcassonne` потрібно зберегти ID
категорії та оновити всі її наявні посилання, включно з текстовими значеннями
в турнірах, новинах та іконках. Дублікат категорії замість перейменування
не створюється. Перейменування і захист реалізовано на етапі 2.

## 4. Поведінка наявних турнірів

### Офіційні турніри збірних

Для `WTCOC`, `ETCOC`, `Asian Cup` і `Copa America` залишаються чинними
адміністратори, ролі, капітани, списки команд, учасники, перевірки асоціацій,
режими Admin/Captain, склади, дедлайни, планування матчів і результати.
Категорія не змінює автоматично фактичний склад команд або географічні
обмеження існуючого турніру.

### Friendly

Планується один турнір `Friendly-Matches` із парою `Teams / Friendly`.
Його ID і чинні публічні прив'язки зберігаються. Капітани продовжують
самостійно планувати матчі за чинними правилами.

Не додавати перевірку унікальності турніру цієї категорії, вимогу мати саме
ID `Friendly-Matches` для будь-якого Friendly-запису або інші спеціальні
обмеження створення через те, що категорія фактично використовується як технічна.

### Rivals

Зберігаються ID турніру, періоди Challenges та їхні `rivals_tournament_id`,
дуелі, перевірки повторних суперників, таблиці результатів і параметри TPR.
Категорія не скидає і не перевизначає `standings_scoring` та інші збережені
налаштування. Міграція класифікації не запускає перерахунок результатів або рейтингів.

### Інші налаштування

Два поля замінюють лише класифікацію. Назви, посилання, логотипи, видимість,
формат, розміри команд і складів, правила, реєстрація, спосіб підрахунку очок
та інші чинні налаштування залишаються окремими даними турніру.

Підсистема `in_person_*` не мігрується в межах цього переходу.

## 6. Наступні етапи

1. **Етап 1 — зафіксувати модель:** виконано цим документом.
2. **Етап 2 — довідник:** реалізовано системні категорії у спільному довіднику,
   перейменування `KoC` і захист записів у API; довідник застосовано на сервері.
   Оновлений UI опубліковано й перевірено на етапі 6.
3. **Етап 3 — сервер:** реалізовано спільні правила `type / category`,
   перевірки API та сумісність зі старою моделлю; перевірено на тестових базах.
4. **Етап 4 — міграція:** готові read-only звіт за фактичними ID, автоматичний
   перевірений backup, повторно виконувана транзакція і rollback через журнал.
   Перевірено на тестових базах, копії фактичної БД та застосовано до робочої БД 16.10.2026.
5. **Етап 5 — інтерфейси:** реалізовано type/category в Admin Tournaments,
   My Tournaments, меню та фільтрах; перевірено тестами й у локальному браузері.
   Спеціальна логіка майбутніх категорій залишається відкладеною.
6. **Етап 6 — перевірка і перемикання:** backend, міграція й публікація HTML
   виконані. Інтерфейси, Friendly, Rivals та публічні сторінки перевірено;
   поточна видимість CCL передана власнику для уточнення.
   Видалення старих колонок виконувати окремим завершальним кроком після
   переведення всіх споживачів.

## 7. Результат етапу 2

- [`categories.js`](../auth-server/src/categories.js) створює та оновлює спільний
  довідник в одній транзакції. Усі 11 системних категорій мають `is_tournament = 1`.
  Для наявних категорій зберігаються ID, порядок сортування та дата створення.
- `KoC` перейменовується на `King of Carcassonne` разом із посиланнями в
  `icons`, `news` і `tournaments`, включно з прихованими та видаленими записами.
  Інші поля цих записів залишаються чинними, крім дати оновлення змінених записів.
- API повертає `is_read_only`. Спроба глобального адміністратора змінити або
  видалити системну категорію отримує `403 / SYSTEM_CATEGORY_READ_ONLY`.
  Системні назви та старе ім'я `KoC` зарезервовані також для створення і
  перейменування звичайних категорій (`409 / SYSTEM_CATEGORY_RESERVED`).
- Адмінка показує для системної категорії `View`, неактивні поля та кнопку
  `Close`. Кнопок збереження і видалення немає. Інші категорії залишаються редагованими.
- Сервер очікує завершення міграції довідника після підготовки інших схем і
  перед відкриттям HTTP-порту. Помилка відкочує транзакцію довідника і зупиняє запуск.
  Якщо в базі вже є окремі записи `KoC` та `King of Carcassonne`, міграція
  зупиняється для вирішення дубліката зі збереженням ID.

Повторний запуск не змінює вже мігровані записи довідника та їхні дати оновлення.
Класифікація турнірів, права доступу, видимість, матчі, результати й TPR
на цьому етапі не переводяться на нові правила.

Перед публікацією backend потрібна узгоджена резервна копія фактичної SQLite-бази:
міграція довідника застосовується автоматично під час запуску нової версії.
Після backend потрібно опублікувати оновлений snippet `gg-html/admin.html`.

Перевірки етапу: тести `categories.test.js` і `categories-admin-ui.test.js`
перевіряють міграцію, її повторний запуск і відкат, захист API та UI і звичайні
операції з іншими категоріями. Окремо перевірено два запуски сервера на тимчасовій
базі та відповідь `/categories` після кожного запуску.

## 8. Результат етапу 3

Єдине джерело правил — [`tournament-classification.js`](../auth-server/src/tournament-classification.js).
Довідник категорій, JavaScript-перевірки та SQL-фільтри використовують той самий
перелік 11 категорій і їхню відповідність типам.

- `/tournaments`, завантаження доступу та відповіді створення/редагування
  повертають нове поле `type` і канонічну `category`. Старі `tournament_type`,
  `team_type`, `subtype`, `access_type` поки залишаються в API як сумісні значення.
- POST/PATCH приймають `type / category` і чинний формат старих форм.
  Старий `National` переходить у `Individuals / National`, `KoC` приймається
  як alias `King of Carcassonne`, Friendly без категорії визначається за
  старим дружнім режимом. Обмежень на ID або кількість Friendly-турнірів немає.
- Нові записи потребують коректної класифікації. Невідома категорія, неправильний
  тип або суперечливі старі поля повертають `400 / INVALID_TOURNAMENT_CLASSIFICATION`.
  Для наявних історичних записів із невизначеною класифікацією редагування
  метаданих залишається можливим зі збереженням їхнього старого режиму доступу.
- Доступ офіційних турнірів, власні команди капітанів, Friendly, перевірка
  прив'язки Rivals, командні склади та публічні фільтри використовують спільні
  правила. Видимість і призначення ролей залишаються окремими даними.
- Рейтинги матчів і їхній скрипт оновлення визначають командний тип через ту
  саму класифікацію. Сам перехід не запускає перерахунок рейтингів.
- PATCH зберігає пропущені поля, зокрема класифікацію, доступи, видимість,
  склади та TPR. Порожній явно переданий `access_users` дозволяє глобальному
  адміністратору очистити призначення; відсутнє поле цього не робить.
  Доступи у відповідях завантажуються за фактичним ID запису, включно з ID з дефісами.

На етапі 3 нові значення обчислюються з чинних колонок. Створення та явне
збереження турніру синхронізують відповідні legacy-поля в тій самій транзакції;
читання не мігрує записи. Фізичне додавання/перейменування колонок і масовий
перенос наявних турнірів на цьому етапі не виконуються.

Нової спеціальної логіки для CCL, MSO, National, Clubs і King of Carcassonne
не додано. Форми класифікації та меню залишаються для етапу 5.

Тести `tournament-classification.test.js` перевіряють всі пари, legacy-значення,
некоректні запити та відповідність SQL і JavaScript. Тести
`tournament-classification-api.test.js` виконують справжні серверні обробники
на SQLite й перевіряють десять контрольних турнірів, ролі, капітанів, видимість,
старі форми, часткові оновлення і зв'язки Rivals/Challenges.
Окремо перевірено старт і перезапуск сервера на тимчасовій базі та шість
HTTP endpoints: `/tournaments`, `/categories`, `/public/main-page-matches`,
`/public/team-official-matches`, його `/filters` і `/public/friendly-matches`.

## 9. Результат етапу 4

Інструмент: `npm run migrate:tournament-classification`. Без `--apply` він
відкриває наявну БД read-only та будує звіт з фактичними ID, before/after,
блокерами, режимами доступу, кількостями й SHA-256 даних. Apply потребує цього
звіту, створює перевірений SQLite online backup і повторно звіряє план під write lock.

Додана nullable колонка `type`; масове заповнення виконує лише явна команда
міграції. API синхронно записує її та legacy-поля. Startup більше не переписує
класифікацію. Старі колонки залишаються для сумісності.

Міграція зберігає початкову класифікацію в журналі. Rollback відновлює лише її,
залишаючи нові матчі, нові турніри та пізніші зміни метаданих. Відкат блокується,
якщо класифікацію після переносу редагували або запис видалили.

Перевірено перенесення десяти погоджених турнірів, National і KoC, роботу з WAL,
повторні запуски, stale/редаговані плани, конкурентний запис після backup,
недоступний backup, атомарний відкат при SQL-помилці чи сторонніх змінах тригером,
збереження даних при rollback, повторний перенос після відкату та обидва напрями CLI.

Порядок запуску на копії й робочій базі: [runbook міграції](./tournament-classification-migration.md).
На етапі 4 робота виконувалася локально без актуальної БД. Подальше застосування
до реальних ID на сервері зафіксовано в результаті етапу 6 нижче.


## 10. Результат етапу 5

- Admin Tournaments і My Tournaments показують лише `type / category` як
  класифікацію. Категорії залежать від типу; їхній перелік і відповідність
  завантажуються зі спільного `/categories` (метадані `tournament_type`
  формує серверний реєстр, окрема колонка довідника не додається).
- У списках прибрані старі `team_type / subtype`; додані фільтри Type і Category.
- Ролі, команди та склади залишаються для офіційних категорій і Friendly.
  Access users редагує лише глобальний адміністратор в офіційних турнірах.
  Збереження інших категорій не очищає приховані ролі, команди, standings або
  налаштування складів. Невідома історична класифікація допускає редагування
  метаданих без її перезапису.
- Меню Player Hub і сторінка командних матчів допускають лише офіційні
  категорії та Friendly. Rivals зберігає Challenges, періоди та TPR;
  CCL, MSO, National, King of Carcassonne і Clubs не отримують командних інструментів.

Перед публікацією snippets потрібен оновлений backend. Для етапу 6 опублікувати
`gg-html/admin.html` та файли `gg-html/player-hub/`: `my-tournaments.html`,
`tournaments.html`, `player-hub.html`, `player-hub-menu.html`.
Production-міграція та публікація в межах етапу 5 не виконувалися.

## 12. Очищення старих колонок

Runtime SQL, читання та збереження турнірів використовують лише `type/category`.
Сервер більше не створює й не записує `tournament_type`, `team_type`, `subtype`, `access_type`
у `tournaments`. Сумісні поля у відповідях API та підтримка старих вхідних форм
залишені як адаптер; вони не потребують фізичних колонок. Метадані `tournament_type`
у `/categories`, типи самих команд і права редакторів новин не змінюються.

`cleanup-tournament-classification.js` окремо видаляє чотири колонки після dry-run.
Перед застосуванням перевіряє канонічні пари, залежні об'єкти схеми, версію SQLite,
цілісність та SHA256 усіх таблиць. Створює перевірений SQLite-бекап з WAL, правами `0600`.
Під `BEGIN IMMEDIATE` повторює перевірку плану; після DROP перевіряє всі збережені
дані, решту схеми й foreign keys. Журнал попередньої міграції зберігається без змін.
Автоматичного видалення під час запуску backend немає.

Перевірено локально: всі 11 категорій; backup, повторний запуск, stale/edited plan,
заблоковані залежності та некоректні пари; повний відкат DDL при помилці другого DROP;
API без старих колонок (створення, редагування, ролі, капітани, Friendly, Rivals/TPR).
Справжній сервер запускався до очищення та двічі після нього: вісім HTTP endpoints
працюють, старі колонки не повертаються. Робочу БД на сервері в цьому етапі не змінено.

Старий v1 adapter збережений лише для історичної міграції. Після очищення її apply/rollback
не доступні; потрібен новий backend, а для аварійного відновлення — бекап перед очищенням.
Короткі серверні команди: [інструкція](./tournament-classification-migration.md).
